# Параметры скорости линии (ConveyerSeven): анализ и внедрённый пакет ускорения

Обоснование и расчёты — по коду репозитория (прошивка `convey15.ino`, `hardware/*`,
`core/cycle/*`), текущей калибровке и паспортным данным компонентов. Все «железные»
изменения вводятся на пустой линии по процедуре из раздела 6.

---

## 1. Что сделано (этот пакет изменений)

| Изменение | Где | Зачем |
|---|---|---|
| SSD2505: DIP **20000 → 10000 имп/об** (1/50 шага) | физически на драйвере | ход ленты требует вдвое меньше импульсов — главный рычаг |
| `normal_steps: 19048 → 9524`, `jog_hold_steps: 1000000 → 500000` | `calibration.json` (обе копии) | пересчёт под новый DIP (та же физическая дистанция) |
| `conveyor_speed: 46000 → 18000`, `conveyor_accel: 46000 → 60000` | `calibration.json` | исполнимый профиль: ход ленты ≈ 1,36 с вместо ~2,5–2,9 с |
| `axis_speed: 1000 → 1300`, `axis_accel: 500 → 5000` | `calibration.json` | перекладка заслонки ≈ 0,54 с вместо 1,66 с |
| `stage_trace_time: 0.1 → 0.0` | `calibration.json` | −0,7 с на каждый шаг (7 переходов фаз × 0,1 с) |
| `#define GS_FAST_PROFILE 10` | `firmware/convey15.ino` (v2.6.0) | разгон/торможение до ~37000 шаг/с вместо ~18000 |
| `I10 [P<axis>]` — короткий ответ по одной оси | прошивка v2.6.0 + `hardware/axis.py` | ответ 170 Б → 85 Б: меньше блокировка Serial при движении осей |
| `G9 S20` при инициализации ленты | `hardware/conveyor.py` | пауза WAIT после хода 100 → 20 мс: подтверждение шага быстрее |
| Опрос `I2` во время движения не чаще каждого 3-го цикла | `hardware/conveyor.py` | длинный ответ I2 (~90 Б) блокировал loop() на 2–3 мс — рывки |

Тесты: `python -m pytest` — 833 passed (обновлены ожидания команд конструктора
ленты, добавлены тесты на `I10 P<axis>` и редкий опрос `I2`).

### Ожидаемый эффект (расчёт)

| Составляющая шага | Было | Стало |
|---|---:|---:|
| Ход ленты (движение + протокол) | ~2,8–3,2 с | **~1,5–1,7 с** |
| Перекладка заслонки (при смене маршрута) | ~1,9 с | **~0,75 с** |
| `stage_trace_time` | 0,7 с | **0 с** |
| SETTLE / REVIEW | 0,2 / 0,5 с | без изменений |
| CAPTURE + ANALYSIS (CPU) | X | X — следующий резерв (GPU) |

Ход ленты: 2 деления × 9524 = 19048 имп = 1,905 об; при 18000 имп/с и ускорении
60000 имп/с² профиль трапецеидальный: `19048/18000 + 18000/60000 ≈ 1,36 с`.
Линейно (при барабане Ø60 мм): скорость ≈ 340 мм/с, ускорение ≈ 1,1 м/с² (0,11 g).

## 2. Что нужно сделать физически перед запуском

1. **Обесточить линию** и выставить на драйвере SSD2505 DIP-переключатели
   микрошага в положение **10000 имп/об** (таблица на корпусе драйвера; в
   линейке Yako это стандартное значение между 6400 и 12800).
2. **Перепрошить Arduino Mega** прошивкой `firmware/convey15.ino` v2.6.0
   (быстрый профиль + `I10 P`). Не обязательно, но желательно: без перепрошивки
   ход ленты ≈ 1,5 с вместо 1,36 с, а ответы `I10` остаются длинными.
3. Убедиться, что `calibration.json` в корне и в `conveyor_three/` — из этого
   пакета (см. раздел 7: значения и DIP неразделимы).

> [!ВАЖНО]
> Если запустить новое ПО со старым DIP (20000 имп/об), шаг ленты физически
> уменьшится вдвое — корпуса начнут приходить на позиции мимо камер и
> распределителя. Первая же проверка из раздела 6 это выявляет.

Если в таблице DIP нет 10000 — берите ближайшее (например 5000 или 12800) и
пересчитайте пропорционально: `normal_steps = 9524 × (ppr/10000)`,
`conveyor_speed = <нужные об/с> × ppr`, `jog_hold_steps` — пропорционально.

## 3. Почему именно такие значения (краткое обоснование)

### 3.1. Потолок генерации импульсов — Arduino, а не двигатель

Шаги генерирует `loop()` через GyverStepper2 (без аппаратного таймера).
Обычный профиль библиотеки: **~18000 шаг/с в фазах разгона/торможения**
(пересчёт периода на каждом шаге), ~37000 шаг/с на постоянной скорости.
Прошивка v2.6.0 включает `GS_FAST_PROFILE` — табличный разгон до ~37000 шаг/с,
поэтому профиль 18000/60000 исполняется полностью. NEMA 23 57HSE2N-D25
(2,0 Н·м, 4,2 А, 1,8 мГн, ном. 1000 об/мин) при 1,8 об/с (108 об/мин) работает
с многократным запасом момента; SSD2505 принимает до 200 кГц.

При старом DIP (20000 имп/об) ход 38096 имп в принципе не мог быть быстрее
~2,1–2,4 с — лента упиралась в производительность Mega. Уменьшение микрошага
до 1/50 снимает этот потолок: теперь лимит — комфорт линейной скорости ленты.

### 3.2. Проскальзывание корпусов

Корпуса лежат свободно, значит линейное ускорение должно быть много меньше µg
(µ ≈ 0,3–0,6, предел 3–6 м/с²). При DIP 10000 ускорение 60000 имп/с² = 6 об/с²:

| Барабан | Ускорение | Скорость при 18000 имп/с |
|---|---|---|
| Ø 60 мм | 1,13 м/с² (0,12 g) | 340 мм/с |
| Ø 80 мм | 1,51 м/с² (0,15 g) | 452 мм/с |
| Ø 120 мм | 2,26 м/с² (0,23 g) | 679 мм/с |

Если барабан больше Ø80 мм — снизить `conveyor_accel` до 40000 (ход ленты
≈ 1,51 с, всё ещё вдвое быстрее прежнего).

### 3.3. Пропуск шагов осей (энкодеров нет)

`I10 POS` берётся из планировщика, а не с мотора: физический пропуск шагов
прошивка не видит. Ограничивающие факторы — блокировки Serial при опросе
(теперь ответ одной оси ~85 Б ≈ 2 мс блокировки вместо ~9 мс) и запас в
2 полных шага (16 имп при микрошаге TMC2209 1/8). При 1300 имп/с отставание
за блокировку ~3 имп — запас более чем пятикратный. Выше ~1600 имп/с без
доработки опроса не подниматься.

### 3.4. Скорость настройки, которая «не работает»

Для хода длиной d профиль треугольный, пока `v²/a > d`: время задаёт только
ускорение, а заданная скорость не достигается. Старые значения были именно
такими (46000/46000 при d=38096; 1000/500 при d=360). Новые пары согласованы:
`18000/60000` — трапеция (разгон 2700 имп = 0,3 с), `1300/5000` — трапеция
(разгон 169 имп = 0,26 с).

## 4. Следующие резервы (если понадобится ещё быстрее)

1. **`conveyor_speed: 24000`** (452 мм/с при Ø60): ход ≈ 1,09 с. Только после
   проверки торможения с корпусами на линии (см. 3.2) — запас по проскальзыванию
   падает до ~2–3×.
2. **`axis_speed: 1400`, `axis_accel: 6000`**: перекладка ≈ 0,49 с.
3. **Инференс на GPU** (`VISION_DEVICE=auto` + CUDA-сборка PyTorch, см. README):
   блок CAPTURE+ANALYSIS — теперь главный потребитель времени шага.
4. Дальнейшее уменьшение микрошага ленты (1/25 и грубее) смысла не имеет:
   ограничением становится уже линейная скорость и комфорт останова.

## 5. Откат

Вернуть можно любой уровень: параметры — правкой `calibration.json`, DIP —
переключателем, прошивка не обязана откатываться (хост совместим с v2.5.0 —
`I10` без P парсится, быстрый профиль не мешает старым значениям).

Полный откат к состоянию до пакета (вместе с DIP **20000 имп/об**):

```json
{
  "jog_hold_steps": 1000000,
  "normal_steps": 19048,
  "conveyor_speed": 46000,
  "conveyor_accel": 46000,
  "dist1_open_position": 360,
  "dist2_bad_position": 0,
  "dist2_cleanup_position": 360,
  "settle_time": 0.2,
  "stage_trace_time": 0.1,
  "axis_speed": 1000,
  "axis_accel": 500,
  "review_time": 0.5
}
```

Промежуточный вариант: **DIP 10000 + консервативные значения** —
`conveyor_speed: 14000`, `conveyor_accel: 40000` (ход ≈ 1,6 с; для барабанов
Ø > 80 мм это базовый вариант), `axis_speed: 1200`, `axis_accel: 3000`.

## 6. Порядок ввода в работу (пустая линия, по одному пункту)

> Корпуса не загружены, аварийный стоп доступен.

1. **DIP + прошивка** (раздел 2), запуск приложения.
2. **Геометрия шага**: JOG-ом (стрелки ←/→) прокрутить ленту и остановить.
   Наклеить метку на ленту. Сделать один production-шаг (кнопка «ПУСК» на
   пустой линии без корпусов или через диагностику): метка должна сместиться
   ровно на ту же дистанцию, что и раньше (один шаг между позициями корпусов).
   Сдвиг вдвое меньше — DIP не переключён, дальше не продолжать.
3. **Лента, скорость**: 20–50 шагов подряд. Движение ровное, без «икания» и
   отскока при остановке; после серии вернуться JOG-ом к метке — совпадение.
4. **Оси**: через HMI-диагностику заслонок 50–100 перекладок
   ГОДНО↔БРАК↔ЗАЧИСТКА. Маркером пометить положения заслонок и риски на раме —
   после серии позиции обязаны совпадать (проверка на пропущенные шаги).
   Слышен стук в крайних точках — снизить `axis_accel` до 3000.
5. **С корпусами**: партия 20–50 шт. Проверить, что корпуса останавливаются
   по центрам позиций под камерами (кадры INPUT/SPIDER) и не смещаются
   относительно предыдущего опыта. Корпус на входе виден «на месте» — иначе
   увеличить `settle_time` до 0,3.
6. Только после п. 1–5 — пробовать значения из раздела 4 тем же способом.

Стоит сверить с реальной механикой при ближайшей калибровке.
