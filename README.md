# ConveyerSeven

Система автоматической визуальной инспекции и сортировки корпусов на конвейере. Проект управляет лентой и двухосевым распределителем, получает изображения с семи USB-камер, запускает YOLO-сегментацию и геометрические правила, а затем направляет корпус в один из каналов:

- `GOOD` — годная деталь;
- `BAD` — брак;
- `CLEANUP` — очистка.

Приложение рассчитано на рабочее место под **Windows**, запускается как полноэкранная HMI через `pywebview` и работает с физическим контроллером (Arduino Mega 2560 + RAMPS 1.6) по COM-порту.

> [!CAUTION]
> Программа управляет реальной механикой. Перед запуском должны быть доступны независимый аварийный останов, исправные концевики и безопасная зона вокруг ленты и распределителя. Не проверяйте новые координаты осей на загруженной линии.

**Вся документация по проекту собрана в этом файле** — отдельных README в подкаталогах нет.

## Актуальная реализация

Текущая версия использует **один свежий набор кадров на каждую стадию детали**.

Основные свойства текущей версии:

- 7 камер с фиксированными ролями и разрешением `1280×720`;
- 12 production-правил и служебное правило наличия детали;
- inference выполняется на CPU (`VisionCluster(device="cpu")`);
- камеры открываются последовательно: одна попытка через стандартный backend OpenCV, успешного `isOpened()` достаточно;
- официальный захват и drain тоже последовательные: один `cap.read()` в момент времени на всю линию;
- каждая занятая стадия (INPUT, затем SPIDER/TOP) проходит полный конвейер `кадр → модели → геометрия → решение → запись` до старта следующей;
- live-просмотр заморожен на весь инспекционный блок и возвращается только на следующем `MOTION`;
- ошибка камеры, модели, COM-порта или обязательного правила переводит цикл в `FAULT`;
- автоматического восстановления камеры во время production-цикла нет;
- архив хранит кадры и `meta.json`, но не формирует dataset-аннотации или `samples.jsonl`;
- UI состоит из обычных JS/CSS-модулей и не требует Node.js или bundler.

## Схема линии

Один корпус проходит три логические позиции:

```text
+0  INPUT       две входные камеры, наличие детали и входные дефекты
+4  SPIDER/TOP  четыре боковые камеры и одна верхняя камера
+7  SORT        подготовка маршрута распределителя
+8  EXIT        корпус покидает учёт после подтверждённого шага
```

Первый шаг после нажатия «ПУСК» выполняется **без движения ленты**. Это позволяет проверить корпус, который уже находился под входными камерами до запуска.

На каждом последующем шаге:

1. подготавливается маршрут корпуса на позиции `+7`;
2. лента выполняет один шаг;
3. контроллер подтверждает остановку;
4. выдерживается пауза затухания вибрации;
5. live полностью замораживается;
6. для каждой занятой стадии **по очереди** (сначала INPUT, потом SPIDER/TOP):
   - камеры этой стадии читаются **по одной**;
   - по этому набору запускаются только модели и правила стадии;
   - строится геометрия, принимается решение, результат пишется в `Part` и архив;
7. следующая стадия не начинается, пока предыдущая не записала результат;
8. результат показывается оператору в течение `review_time`;
9. live возобновляется только на следующем движении ленты.

Фазы, контролируемые `StepSequencer`:

```text
MOTION → SETTLE → CAPTURE → ANALYSIS → [CAPTURE → ANALYSIS] → PUBLISH
```

Второй `CAPTURE → ANALYSIS` — это следующая занятая стадия того же шага, не параллельный захват. Пауза просмотра выполняется между последним анализом и публикацией, но отдельным значением `StepStage` не является. Live остаётся замороженным от первого официального кадра до следующего `MOTION`, чтобы стоп-кадры ревью не затирались потоком.

В блоке «ЭТАПЫ ЦИКЛА» HMI отображаются текущий код фазы, человекочитаемое действие, номер шага и прогресс `СТАРТ → ХОД → СТОП → КАДР → АНАЛИЗ → РЕВЬЮ → ИТОГ`; на `СТАРТ` отдельно видно, что первый кадр берётся без движения ленты. Внутри анализа дополнительно видны этапы `МОДЕЛИ`, `ПОСТРОЕНИЕ ГЕОМЕТРИИ`, `РЕШЕНИЕ` и `ЗАПИСЬ РЕЗУЛЬТАТА` для INPUT и SPIDER/TOP.

## Камеры и модели

### Роли камер

| Роль | Позиция | Назначение |
|---|---:|---|
| `INPUT_LEFT` | `+0` | левая входная сторона |
| `INPUT_RIGHT` | `+0` | правая входная сторона |
| `SPIDER_LEFT` | `+4` | длинные контакты слева |
| `SPIDER_RIGHT` | `+4` | длинные контакты справа |
| `SPIDER_IN` | `+4` | короткие контакты внутри |
| `SPIDER_OUT` | `+4` | короткие контакты снаружи |
| `TOP` | `+4` | верхняя геометрия, раковины и стекло |

Соответствие ролей индексам устройств хранится в `camera_mapping.json`. Индексы зависят от конкретного ПК и USB-подключения.

### Файлы весов

Веса не входят в репозиторий. Их необходимо разместить по путям из `vision/model_config.py`:

```text
weights/

│   └── window_sinks.pt                              # objects
├── 2,7/
│   ├── long_omission_v.1.2.pt                       # omission-long
│   └── contacts_long_v.1.pt                         # contacts-long
├── 3,5/
│   ├── short_omission_v.1.2.pt                      # omission-short
│   └── contacts_short.pt                            # flatness_short
└── 4/
    ├── contacts.pt                                  # contacts
    ├── platform_old.pt                              # platform
    ├── sinks_v.1_m.pt                               # shells
    ├── glass_v.1.pt                                 # glass
    ├── well_v.1.pt                                  # case, case_central
    └── pins.pt                                      # pin
```

При запуске проверяются наличие каждого файла и точный порядок имён классов. Несовпадение останавливает инициализацию до движения оборудования.

## Правила инспекции

| Камеры | Правило | Что проверяется |
|---|---|---|
| INPUT | `part_presence` | служебное подтверждение наличия детали обеими камерами |
| INPUT | `window_geometry` | количество и размеры семи окон |
| INPUT | `window_sinks` | пересечение раковин с окнами |
| SPIDER LEFT/RIGHT | `contacts_long` | ряд из пяти длинных контактов |
| SPIDER LEFT/RIGHT | `long_omission` | граница длинной omission-полосы |
| SPIDER IN/OUT | `contacts_short` | пара коротких контактов |
| SPIDER IN/OUT | `short_omission` | граница короткой omission-полосы |
| TOP | `top_contacts` | раскладка контактов `5L + 5R + 2T + 2B` |
| TOP | `top_platform` | вписывание эталона в mask платформы |
| TOP | `platform_contacts_overlap` | выход платформы за область, построенную по контактам |
| TOP | `sinks` | раковины внутри `case_central` вне защищённых зон |
| TOP | `glass` | стекло на platform / pins / кольце case — маршрут `CLEANUP` |
| TOP | `glass_on_contacts` | стекло на контактах — маршрут `BAD` |

Если обе INPUT-камеры не подтверждают наличие детали, лоток считается пустым: `Part` не создаётся, остальные входные правила не выполняются, увеличивается счётчик пустых лотков.

Все обычные дефекты ведут в `BAD`. В `CLEANUP` идёт деталь, у которой **все** обнаруженные дефекты входят в набор `CLEANUP_DEFECTS` из `domain/part.py` — это `glass` (его эмитит правило `TopGlassRule`). Деталь без дефектов получает `GOOD` только после завершения обеих стадий инспекции.

Пороговые значения находятся в `thresholds.json`, сгруппированы по ролям камер. Поля проверяются при загрузке. Пороги можно менять в HMI в состояниях `IDLE` / `STOPPED`; изменения сохраняются в файл и пересоздают `DecisionEngine`. Список `disabled_rules` отключает правила по имени, но запуск блокируется, если активных правил не осталось.

## Логика распределителя

Этот раздел — **источник истины** для логики маршрутизации корпуса. При изменении `hardware/distributor.py`, `core/cycle/` (оркестратор и шаг), UI или тестов эта механика не должна переопределяться комментариями или визуальными метафорами.

### Оси

#### DIST1 — первая заслонка

DIST1 не удерживает корпус, не является лепестком и не открывается «для сброса» в старом смысле.

| Координата DIST1 | Путь корпуса |
|---|---|
| `0` | корпус падает в **GOOD** |
| `340` | корпус направляется на вторую заслонку **DIST2** |

#### DIST2 — вторая заслонка

DIST2 влияет на корпус **только** когда DIST1 уже направляет его на DIST2 (`DIST1=340`).

| Координата DIST2 | Путь корпуса |
|---|---|
| `0` | **BAD** |
| `340` | **CLEANUP** |

### Маршруты

| Категория | DIST1 | DIST2 |
|---|---:|---:|
| `GOOD` | `0` | не влияет |
| `BAD` | `340` | `0` |
| `CLEANUP` | `340` | `340` |

Имя `dist1_open_position` в `calibration.json` — совместимое имя параметра. Физически это положение DIST1 **«на DIST2»**, а не «открытая заслонка сброса».

### Очередность для корпуса на +7

1. Корпус на позиции `+7` ожидает следующий шаг ленты. Механического удержания заслонкой нет.
2. До команды движения полностью выставляется его маршрут. Заслонки, которым нужно сменить позицию, двигаются **одновременно** — команды `G27` на обе оси отправляются подряд, остановка ожидается после обеих:
   - GOOD: DIST1 → 0;
   - BAD: DIST1 → 340 и DIST2 → 0 одновременно;
   - CLEANUP: DIST1 → 340 и DIST2 → 340 одновременно.

   Оси, уже стоящие в целевой позиции, не получают команду и не двигаются: серия одинаковых маршрутов (например, BAD после BAD) вообще не шевелит заслонки, а смена канала BAD↔CLEANUP двигает только DIST2.
3. Затем подаётся команда шага конвейера.
4. После подтверждённой остановки (`I1`, строгая проверка `I2` и совпадение завершённого `STEP`) система подтверждает передачу, обновляет счётчики и архивирует корпус. Отдельной паузы на падение нет: заслонки не двигаются до `ROUTE_PREPARE` следующего шага, то есть только после полного завершения выбрасывающего шага (`SETTLE` → `CAPTURE` → `ANALYSIS` → `REVIEW` → `PUBLISH`).
5. Заслонки не возвращаются автоматически после каждого корпуса. Они остаются в текущем положении, пока маршрут следующего корпуса не требует изменения.

### Одновременное движение заслонок

Заслонки двигаются параллельно. В момент подготовки маршрута лента стоит, корпус, для которого выставляется маршрут, находится на `+7` и заслонок ещё не достиг, а маршрут предыдущего корпуса уже полностью отработал. Поэтому прежнее ограничение «не перемещать DIST2, пока DIST1 открывает путь на неё» снято: и в рабочем цикле (`prepare_route`), и при подготовке к пуску (`park_production`) оси, которым нужно сменить позицию, едут одновременно, без предварительного возврата DIST1 в `GOOD=0`. Это допустимо, поскольку корпус в этот момент физически не находится на заслонках.

Ручная диагностика заслонок (`diagnostic_gate` / `diagnostic_route`) не изменилась: она разрешена только на пустой линии (`IDLE`/`STOPPED`, без корпусов), и каждая группа кнопок двигает только свою заслонку — кнопки верхнего распределителя (ГОДНО/БРАК) управляют только DIST1, кнопки нижнего (БРАК/ЗАЧИСТКА) — только DIST2. Нижние кнопки не возвращают DIST1 в GOOD: положения заслонок при ручной проверке контролирует оператор.

## Требования

### Программные

- Windows 10/11;
- Python **3.11** с доступной командой `py`;
- драйверы семи UVC-камер;
- доступ к COM-порту контроллера;
- локальные `.pt`-веса из раздела «Камеры и модели».

Python-зависимости перечислены в `requirements.txt`: OpenCV, NumPy, pyserial, Ultralytics, FastAPI/Uvicorn и pywebview.

### Аппаратные

- 7 USB-камер, способных одновременно работать в `MJPG 1280×720 @ 30 FPS`;
- контроллер (Arduino Mega 2560 + RAMPS 1.6, прошивка `convey15` v2.5.0+), отвечающий на `I2` полями `MOV=`, `WAIT=`, `STEP=` и `lastErr=`;
- конвейер;
- две оси распределителя с рабочими концевиками.

Для семи камер критична пропускная способность USB. При нестабильности распределите камеры между корневыми USB-контроллерами и исключите пассивные хабы.

## Установка

Из корня проекта:

```bat
setup.bat
```

Скрипт создаёт `.venv` на Python 3.11, обновляет `pip` и устанавливает `requirements.txt`.

Ручной эквивалент:

```bat
py -3.11 -m venv .venv
.venv\Scripts\python.exe -m pip install --upgrade pip
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

После установки разместите веса и проверьте конфигурационные JSON-файлы.

## Калибровка камер

Если `camera_mapping.json` отсутствует, `run.bat` автоматически запускает оконный мастер до подключения COM-порта и движения механики.

Для принудительного повторного назначения камер:

```bat
run_camera_calibration.bat
```

Мастер ищет устройства ровно так же, как их открывает основная программа: для каждого Camera ID создаётся `cv2.VideoCapture(id)` и проверяется `isOpened()`, затем применяется рабочий формат `1280×720 MJPG`. Живой кадр читается только для назначения ролей оператору, а частичная конфигурация не сохраняется.

Для быстрой проверки камер без оконного мастера (например, по консоли/удалённо) используйте `camera_check.bat` — он выводит отчёт по каждому Camera ID и по ролям из `camera_mapping.json`, ничего не изменяя.

## Запуск

Два режима запуска — двумя разными батниками:

```bat
run.bat        REM РЕЖИМ ОТЛАДКИ — пороги, геометрия правил, паузы отсмотра
run_work.bat   REM РЕЖИМ РАБОТЫ — чистый видеопоток, без разметки и простоев
```

Оба запускают `.venv\Scripts\python.exe main.py`; `run_work.bat` дополнительно
ставит `CONVEY_MODE=work`. Различия режимов — в разделе
«Режимы ОТЛАДКА / РАБОТА».

`run.bat` запускает `.venv\Scripts\python.exe main.py`. Сначала проверяется `camera_mapping.json`: если файла нет, запускается оконный мастер калибровки (COM-порт и механика в этот момент ещё не затронуты). После открытия HMI фоновая инициализация загружает `calibration.json`, а настройки архива — на этапе `inspection`.

Splash-экран ведёт восемь этапов инициализации (`application/startup.py`):

| Этап | Действие |
|---|---|
| `cameras` | однократное открытие семи камер без прогрева и чтения тестовых кадров |
| `models_load` | загрузка YOLO-моделей |
| `models_warm` | прогрев моделей |
| `inspection` | настройка системы контроля (пороги + `DecisionEngine`) |
| `serial` | поиск контроллера по ответу на `I2` |
| `hardware` | настройка ленты, осей и ручного JOG |
| `cycle` | физический homing DIST1/DIST2 и создание производственного цикла |
| `ready` | запуск системы |

При ошибке splash-экран показывает этап и причину, а production-цикл не запускается.

Горячие клавиши основного окна (`bootstrap.js`):

- `F5` — пуск;
- `F6` — остановка;
- `F7` или `P` — пауза / продолжить;
- `F11` — полноэкранный режим окна;
- `Tab` — переключение режима кадра `RAW` ↔ `ПРАВИЛА` (когда переключение разрешено);
- `←` / `→` (или `A` / `D`) — навигация по камерам; при активном JOG — удерживаемый ручной ход ленты;
- `1`–`9` — прямой выбор камеры;
- `Esc` — закрывает открытую модалку (галерею, настройки архива), иначе инициирует штатный выход; повторное нажатие — принудительный.

Штатная остановка перестаёт принимать новые детали и выводит уже учтённые корпуса с линии. В `FAULT` повторять физический шаг нельзя: соответствие корпуса позиции уже не гарантировано.

## Режимы ОТЛАДКА / РАБОТА

Приложение запускается в одном из двух режимов, выбираемых на этапе запуска
(разными батниками), а не переключаемых оператором на лету.

| | ОТЛАДКА (`run.bat`) | РАБОТА (`run_work.bat`) |
|---|---|---|
| Видеопоток со всех камер | да | да (чистый, без отрисовки) |
| Геометрия правил (debug-overlay) | рисуется | не рисуется |
| RAW-детекции | рисуются | не рисуются |
| Панель «Анализ кадра» / «Пороги правил» | есть | скрыты |
| Переключатель ВИД RAW/ПРАВИЛА | есть | скрыт |
| Ручные кнопки распределителя (диагностика) | есть | скрыты |
| Пауза отсмотра `review_time` | из `calibration.json` | `0` |
| Отладочная пауза `stage_trace_time` | из `calibration.json` | `0` |
| Статистика, ПУСК/СТОП/пауза, JOG, путь корпусов | есть | есть |

Режим задаётся переменной окружения `CONVEY_MODE` (`work` — РАБОТА; любое
другое значение или отсутствие — ОТЛАДКА). `run_work.bat` — это
`run.bat` с `set CONVEY_MODE=work`.

Важно: инспекция, маршрутизация и архив в режиме РАБОТА **не меняются** —
решение по деталям принимается как обычно, а кадры с разметкой
(`<ROLE>_debug.jpg`, `<ROLE>_raw.jpg`) и полоса «последние корпуса» остаются
с разметкой в обоих режимах. Отключается только отрисовка поверх живого
изображения для оператора и отладочные паузы цикла. Заморозка live на
инспекционный блок (`CAPTURE…PUBLISH`) в обоих режимах одинаковая.
`settle_time` (гашение вибрации) — физический параметр и не обнуляется.

## Симуляция UI без оборудования

Для проверки интерфейса без камер, COM-порта, моделей и pywebview есть полностью автономный симулятор:

```bat
.venv\Scripts\python.exe ui_simulation.py --host 0.0.0.0 --port 8000
```

Добавьте `--work`, чтобы увидеть UI в режиме РАБОТА (чистый поток, без
разметки и отладочных панелей).

`ui_simulation.py` обслуживает тот же FastAPI-интерфейс, что и production, но имитирует транспорт, ленту и движение деталей. Кнопки «ПУСК», «Пауза», «Продолжить» и «СТОП» работают как на реальной линии. Откройте в браузере `http://<host>:<port>`.

## Конфигурация

### `calibration.json`

| Поле | Назначение |
|---|---|
| `jog_hold_steps` | длина непрерывного сегмента ручного хода |
| `normal_steps` | шаги ленты на одно деление |
| `conveyor_speed`, `conveyor_accel` | скорость и ускорение ленты |
| `dist1_open_position` | координата DIST1 «НА DIST2» (см. «Логика распределителя») |
| `dist2_bad_position` | координата канала BAD |
| `dist2_cleanup_position` | координата канала CLEANUP |
| `settle_time` | пауза после остановки перед кадром, `0..5` с |
| `stage_trace_time` | отладочная пауза перед фазами, `0..5` с |
| `review_time` | просмотр результата, `0..30` с; если поля нет — 2 с |
| `axis_speed`, `axis_accel` | скорость и ускорение осей |

Для production рекомендуется `stage_trace_time: 0`. Значения координат должны соответствовать реальной механике; скрытых безопасных fallback-координат нет.

### `camera_mapping.json`

JSON-объект `роль → индекс устройства` для всех семи ролей. Индексы определяются мастером калибровки и зависят от конкретного ПК и порядка USB-подключения.

### `thresholds.json`

Секции по ролям камер (`INPUT_LEFT`, `INPUT_RIGHT`, `SPIDER_LEFT`, `SPIDER_RIGHT`, `SPIDER_IN`, `SPIDER_OUT`, `TOP`) плюс список `disabled_rules`. Внутри секций — пороги правил с русскими подписи для UI и проверкой диапазонов при загрузке; фиксированные количества (2 коротких контакта, 14 TOP) вшиты в лоадер. Пользовательские подписи задаются ключами `_label.<имя_параметра>`.

### `archive_config.json`

```json
{
  "enabled": true,
  "root_path": "archive",
  "jpeg_quality": 92,
  "compress_on_shutdown": true,
  "delete_original_after_zip": true
}
```

Качество JPEG ограничивается диапазоном `70..98`. При включённом сжатии партия на выходе упаковывается в обычный ZIP Deflate уровня 6. Если `delete_original_after_zip=true`, распакованная папка удаляется после успешной проверки ZIP.

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `SERIAL_PORT` | COM-порт, который нужно проверить первым |
| `SERIAL_BAUD` | baudrate, по умолчанию `115200` |
| `CAMERA_BACKENDS` | порядок backend-ов для `camera_check.bat` (диагностики), например `dshow,msmf`; мастер калибровки и основной запуск открывают камеры стандартным backend OpenCV |
| `CONVEY_MODE` | режим запуска: `work` — РАБОТА (чистый поток, без отладочных пауз и разметки), иначе — ОТЛАДКА. Задаётся батниками `run.bat` / `run_work.bat` |

Примеры:

```bat
set SERIAL_PORT=COM4
run.bat
```

```bat
set CAMERA_BACKENDS=dshow,msmf
camera_check.bat
```

## Архив

Для каждой партии создаётся структура:

```text
<root>/
├── stats.json
└── <YYYY-MM-DD>/<batch_id>/
    ├── batch.json
    ├── GOOD/part_0001/
    ├── BAD/part_0002/
    └── CLEANUP/part_0003/
```

Папка детали содержит:

```text
meta.json
<ROLE>.jpg          # исходный кадр
<ROLE>_raw.jpg      # сырые YOLO-детекции, если сформированы
<ROLE>_debug.jpg    # геометрия правил, если сформирована
```

В `meta.json` записываются категория, решение, дефекты, этап и роли камер. Неизвестная или аварийно завершённая категория сохраняется в `BAD`, а исходное значение остаётся в `requested_category`.

Текущая упрощённая версия **не сохраняет** detection JSON, `samples.jsonl` и pseudo-labels.

## HMI и ручное управление

Интерфейс показывает:

- семь live-превью и выбранный основной кадр; подписи камер показывают
  только роль (например `ВХОД · СЛЕВА`). Физический Camera ID (индекс
  устройства из `camera_mapping.json`) в названиях камер в UI не
  показывается по требованию оператора; соответствие «роль ↔ физическая
  камера» задаётся в `camera_mapping.json` и отдаётся в `/api/cameras`
  (поле `camera_ids`);
- режимы `RAW` и `ПРАВИЛА` во время анализа;
- путь деталей по позициям линии;
- текущую фазу и состояние цикла;
- блок распределителя: два ползунка с постоянными подписями концов — верхний `ГОДНО` (слева) / `БРАК` (справа), нижний `БРАК` (слева) / `ЗАЧИСТКА` (справа); положение бегунка показывает координату оси, текстовые значения координат, состояний и последней команды в HMI не выводятся;
- статистику GOOD/BAD/CLEANUP и пустых лотков;
- последние детали и архивные изображения;
- редактор порогов;
- удерживаемый dead-man JOG.

Ручной JOG доступен в безопасных состояниях `IDLE` / `STOPPED`, а также во время паузы (`PAUSED`) — пауза специально предназначена для ручной коррекции ленты (на backend это `JOG_ALLOWED_STATES = ("IDLE", "STOPPED", "PAUSED")`). Диагностика распределителя кнопками DIST1/DIST2 — только в отладочном режиме и только в `IDLE` / `STOPPED`, когда на линии нет учтённых деталей и JOG не занят. В режиме РАБОТА блок распределителя всегда компактный, как во время рабочего процесса, и кнопки не появляются. При отпускании кнопки, потере фокуса или heartbeat отправляется команда остановки.

### Пауза в рабочем цикле

Пауза (`request_pause`) применяется на границе шага — **после** завершения движения ленты и затухания вибрации, но **до** начала захвата и анализа кадров. Когда оператор нажимает «Пауза», барьер `_check_pause_barrier()` срабатывает после фазы `SETTLE` перед фазой `CAPTURE`.

При входе в паузу:

1. live-просмотр продолжается в режиме JOG;
2. **геометрия разметки предыдущего шага очищается** (`clear_overlays`): она построена по статичному кадру и на live-изображении указывала бы мимо детали;
3. оператор может вручную подвинуть ленту кнопками JOG;
4. после паузы следующий шаг всегда начинается с нового официального CAPTURE — старые live-кадры и результаты наличия не переиспользуются.

При нажатии «Продолжить» (`request_resume`) цикл возобновляется с полного свежего захвата и анализа. Новая разметка появляется только после завершения анализа — геометрия не «прилипает» от предыдущего шага.

## Архитектура HMI (frontend)

UI использует упорядоченные классические браузерные модули и **не требует** production-bundler (Node.js не нужен).

### Порядок загрузки JavaScript

1. `core.js` — константы, состояние, DOM-кэш, API и общие помощники.
2. `boot.js` — splash, опрос готовности backend (boot polling).
3. `diagnostics.js` — диагностика распределителя и анализ выбранного кадра.
4. `status.js` — статус backend, OFFLINE, телеметрия процесса и путь детали.
5. `controls.js` — START/STOP/EXIT, ошибки и overlay состояния.
6. `thresholds.js` — панель порогов, inline-редактирование и сохранение.
7. `cameras.js` — выбор камеры, режимы RAW/ПРАВИЛА и обновление кадров.
8. `frame-analysis.js` — структурные метрики по объектам и карточка анализа.
9. `jog.js` — dead-man hold/heartbeat/release логика.
10. `history.js` — последние детали, архивная галерея и полноэкранный просмотр.
11. `archive.js` — настройки папки партий, качества JPEG и ZIP.
12. `bootstrap.js` — горячие клавиши, инициализация и test-only hook.

Функции могут вызывать функции из более поздних модулей только после загрузки всех скриптов, когда `bootstrap.js` запускает UI. **Не меняйте порядок** в `vision/ui/templates/index.html`.

### Блочная карта UI

Каждая крупная зона имеет `data-ui-block`, чтобы её можно было отдельно проверять, ограничивать и не допускать наложения динамических надписей:

- `splash` — экран запуска и ошибка инициализации.
- `operator-header` — статус линии, заголовок и метрики.
- `preview-strip` — семь миниатюр камер.
- `main-camera` + `camera-controls` — главный кадр, режимы RAW/ПРАВИЛА и анализ кадра.
- `process-line` — трафаретный путь корпусов: девять нейтральных окон (`+0 · ВХОД` … `+8 · СБРОС`) и фрагменты корпусов за стенкой. Цвет корпуса показывает только вердикт. После синхронного горизонтального шага новый корпус падает в `+0`, а корпус из `+8` — под вагон; конфликт двух корпусов в одном окне скрывает их оба.
- `history-strip` — последние детали.
- `process-phase` — панель состояния ленты.
- `right-panel` — прокручиваемая правая колонка.
- `cycle-stats`, `defects`, `service-stats`, `distributor`, `thresholds`, `frame-analysis`, `jog` — независимые блоки правой колонки.
- `operator-footer` — кнопки ПУСК/СТОП/ВЫХОД и горячие клавиши.
- `footer-archive` — сервисная группа футера: кнопка `АРХИВ` вынесена из ряда операторских кнопок в правый край, за вертикальный разделитель.

- `archive-settings` — выбор папки хранения и политики сжатия партий.

Правило для новых зон: сначала добавить `data-ui-block`, затем проверить, что длинные русские подписи либо обрезаются через `ellipsis`, либо переносятся через `overflow-wrap: anywhere`.

### Профессиональная HMI-компоновка

- Системные шрифты `Segoe UI` и `Cascadia Mono` работают без сети.
- Нейтральная палитра используется для штатной работы.
- Зелёный, жёлтый и красный зарезервированы для результата и состояния.
- Основной кадр имеет максимальную доступную площадь.
- Статистика использует сетку 2 + 3 показателя.
- В рабочем цикле анализ, статистика и распределитель остаются одновременно видимыми.
- Инженерские и ручные элементы скрываются, когда они не нужны оператору.

### Стандарт операторских обозначений

Внутренние коды API и firmware остаются неизменными, но оператору показываются только согласованные русские названия:

| Внутренний код | Надпись в интерфейсе |
|---|---|
| `IDLE` | `ГОТОВА К ПУСКУ` |
| `RUNNING` | `РАБОТАЕТ` |
| `PAUSED` | `ПАУЗА · КОРРЕКЦИЯ ЛЕНТЫ` |
| `STOPPING` | `ОСТАНОВКА ЛИНИИ` |
| `STOPPED` | `ОСТАНОВЛЕНА` |
| `FAULT` | `АВАРИЯ` |
| `DIST1_HOME` | `ГОДНО` |
| `DIST1_OPEN` | `БРАК` |
| `DIST2_BAD` | `БРАК` |
| `DIST2_CLEANUP` | `ЗАЧИСТКА` |
| `GOOD` | `ГОДНО` |
| `CLEANUP` | `НА ЗАЧИСТКУ` |

Названия камер задаются через `CAMERA_ROLE_LABELS`. Аббревиатуры без расшифровки в операторских надписях не используются; исключения — технические идентификаторы `RAW`, `DIST1` и `DIST2`.

### Правила изменений UI

- Доступность движения должна приходить из backend `line_status.controls`.
- Новые физические действия должны стартовать отключёнными в HTML.
- У физического действия должны быть: валидация состояния на backend, локальный pending-lock и показ ошибок API.
- Polling-запросы не должны перекрываться.
- Динамические операторские данные выводятся через `textContent`, не через небезопасный `innerHTML`.

## Прошивка контроллера

Прошивка `firmware/convey15.ino` (`FW convey15 v2.5.0`) для **Arduino Mega 2560 + RAMPS 1.6** управляет конвейером и двухосевым распределителем.

### Оборудование и распиновка

| Устройство | Подключение |
|---|---|
| Конвейер NEMA 23 (57HSE2N-D25) + SSD2505 | STEP=16, DIR=17 (мимо RAMPS, 24V) |
| NEMA 17 #0 (слот X, TMC2209) | STEP=54, DIR=55, EN=38 |
| NEMA 17 #1 (слот Y, TMC2209) | STEP=60, DIR=61, EN=56 |
| Концевики | D3 (X-), D14 (Y-), INPUT_PULLUP LOW |
| Серво ×5 | 23, 25, 27, 29, 31 (резисторы 10к к GND от наводок) |

Скорость порта — **115200** baud.

> [!IMPORTANT]
> Для защиты сервоприводов от дёрганья при включении установите подтягивающие резисторы 10 кОм от каждого сигнального пина серво к GND: во время загрузчика (~2 с) пины Arduino висят в INPUT, и серво ловят наводки.

### Протокол

G-коды конвейера `G0..G13`, оси `G20..G33`, информация `I0..I12`. Подробный список — в шапке `firmware/convey15.ino`. Ключевые команды:

| Команда | Назначение |
|---|---|
| `G0` / `G1` | мягкая / аварийная остановка конвейера с reset позиции |
| `G3 N<seq>` | production-ход (RELATIVE) с адресованным `ACK G3 STEP=<seq>`; `G3` без `N` оставлен для JOG |
| `G4`/`G5`/`G6`/`G7` | ускорение, макс. скорость, делений за ход, микрошагов на деление |
| `G8` / `G12` | направление, режим автопауз |
| `G20` / `G27` | движение оси RELATIVE / ABSOLUTE (`P0`=X, `P1`=Y, без `P` — все) |
| `G21` / `G22` / `G23` | скорость, ускорение, направление оси |
| `G24` / `G25` | мягкая / аварийная остановка оси |
| `G26` | включение/выключение драйвера |
| `G28` | умный хоминг (3 фазы: быстрый → отскок → точный) |
| `G29..G33` | скорость хоминга, отскок, программные лимиты оси |
| `I1` / `I2` | короткий и расширенный статус конвейера; `I2.STEP` меняется только после физического завершения G3 |
| `I6` / `I7` | версия прошивки, последняя ошибка |
| `I10` / `I11` / `I12` | статус осей, конфигурация осей, состояние концевиков |

Хост-софт (`hardware/conveyor.py`, `hardware/axis.py`, `hardware/distributor.py`) работает поверх `SerialTransport`. Для каждого production-шага он читает текущий `I2.STEP`, отправляет следующий номер в `G3 N<seq>`, проверяет адресованный ACK и не меняет логическую позицию до появления того же завершённого `STEP` в `I2`. Потеря команды, ACK, перезапуск контроллера или остановка незавершённого хода переводят цикл в `FAULT` без опасного автоматического повтора. Для хоминга используется `G28`, для движения осей — `G20`/`G27`.

### Загрузка прошивки

1. Открыть `firmware/convey15.ino` в Arduino IDE.
2. Установить библиотеки через Library Manager: `GyverStepper2` (GyverLibs), `Servo`.
3. Выбрать плату *Arduino Mega 2560*, порт COM.
4. Загрузить.

### Версионирование прошивки

Версия задаётся в шапке файла: `FW_VERSION = "2.5.0"` + `FW_DATE = __DATE__ " " __TIME__`. При изменении прошивки обновляйте `FW_VERSION` и документируйте изменение в git-коммите.

## Отличия упрощённой версии от расширенной

Текущая реализация в корне репозитория — упрощённый вариант предшествующей расширенной системы. Сводка отличий:

**Сохранено по смыслу без изменений:**

- тёмная HMI, компоновка, модули JS/CSS и HTML (из панели архива убраны только поля выбора метода/уровня ZIP);
- правила отбраковки `domain/defect_rules/*`, геометрия, fail-closed поведение, пороги и оверлеи;
- нейросети: `vision/vision_cluster.py`, карта камер/моделей, обработка одного свежего кадра;
- маршрутизация деталей `domain/part.py` (`GOOD` / `BAD` / `CLEANUP`);
- механика распределителя `hardware/distributor.py`, `axis.py`, `conveyor.py` и контракт из раздела «Логика распределителя»;
- фазы производственного шага MOTION / SETTLE / CAPTURE / ANALYSIS / REVIEW / PUBLISH, состояние линии и JOG.

**Упрощено:**

1. **Один кадр на стадию** — production анализирует один свежий набор кадров; `inspection/inspector.py` принимает словарь ролей, `inspection/run_report.py` собирает плоские карточки замеров для HMI.
2. **Камеры (`vision/camera_manager.py`)** — при старте каждая роль один раз открывается обычным `cv2.VideoCapture(id)` и принимается по `isOpened()`. Стартовый прогрев, тестовые кадры, перебор API и повторные открытия отсутствуют. Проверка кадра выполняется только при его фактическом использовании; ошибка рабочего захвата переводит production-cycle в `FAULT`.
3. **Архив (`inspection/part_archive.py`)** — сохраняются `<ROLE>.jpg`, `<ROLE>_raw.jpg`, `<ROLE>_debug.jpg` и `meta.json` в `GOOD/BAD/CLEANUP/part_NNNN/`, остались `batch.json` и накопительный `stats.json`. Убраны несколько методов ZIP (`stored/lzma`), detection JSON, `samples.jsonl`, dataset/pseudo-label подготовка и файлы `*_runN.*`. При выходе может создаваться один обычный ZIP с дефолтным deflated.
4. **Пороги (`domain/threshold_loader.py`)** — сохранены загрузка `thresholds.json`, секции по камерам, русские подписи, группировка для UI, фиксированные количества, ярлыки `_label.*` и проверка диапазонов. Удалены длинные описания `PARAM_DESCRIPTIONS`, часть дублей и ручная схема.
5. **Production cycle** — INPUT и SPIDER больше не делят один общий снимок шага. Каждая занятая стадия читает свои камеры, гоняет свои модели и пишет решение до старта следующей. Камеры читаются строго последовательно; live заморожен на весь инспекционный блок. Сам цикл разбит на части: оркестратор `core/cycle/orchestrator.py` и mixins шага / диагностики / JOG / статуса (`core/production_cycle.py` остаётся совместимым импортом). Публичный API не менялся.

## Диагностика типовых проблем

### `Model file not found`

Проверьте структуру `weights/` и пути в `vision/model_config.py`. Веса не загружаются из сети автоматически.

### `Model class mismatch`

Подключён другой вариант модели. Имена и порядок классов должны точно совпадать с `classes` в `vision/model_config.py`.

### `read returned no frame` или не открылись все камеры

Запустите консольную диагностику до повтора запуска линии:

```bat
camera_check.bat
```

Она изолированно проверяет каждый Camera ID (перебор DirectShow/Media Foundation, формат `1280×720`, яркость), затем отдельно воспроизводит простое последовательное открытие семи ролей через `CameraManager`. Расширенные проверки принадлежат только диагностике и не выполняются при обычном запуске. `camera_mapping.json` не изменяется.

Типовые причины по одному неоткрытому индексу (`DSHOW: устройство не открылось` + `MSMF: read returned no frame`):

- камера отключена, обесточена или неисправен USB-кабель/порт/разветвитель;
- камера занята другой программой (второй экземпляр линии, Zoom/Teams/OBS, приложение «Камера» Windows);
- индексы устарели после переподключения USB или перезагрузки — переназначьте роли мастером `run_camera_calibration.bat`.

Проверьте также питание и распределение по USB-контроллерам. `CAMERA_BACKENDS` влияет только на `camera_check.bat`; мастер калибровки и обычный запуск открывают камеры стандартным backend OpenCV и не перебирают API. Ошибка рабочего захвата требует устранения причины и перезапуска.

### `near-black frame`

Камера открылась, но изображение не прошло проверку яркости. Проверьте освещение, экспозицию, объектив и назначение Camera ID.

### Контроллер не найден

Проверьте COM-порт, baudrate и ответ на `I2`. Можно задать `SERIAL_PORT` и `SERIAL_BAUD`, однако предпочтительный порт всё равно проходит проверку формата ответа.

### Ошибка калибровки или homing

Не запускайте линию повторно до проверки концевиков и реальных координат. Логика маршрутов не должна изменяться в обход раздела «Логика распределителя».
